A WebAssembly engine has to balance three costs: the time it takes to compile a function, the speed of the machine code it produces, and the memory it uses along the way.

A clever optimization isn't much help if the compiler needs a mountain of temporary data to perform it. I want to improve the code a program runs without making the compiler unnecessarily slow or memory-hungry.

That makes an otherwise hidden design choice important: **how should the compiler represent a program while it works on it?**

## The problem we're solving

A compiler should remove work a program doesn't need, while keeping everything that affects its behavior. A bounds check may be unnecessary on one path but essential on another. A value may never be used even though producing it could still trap.

To make these decisions safely, the compiler needs to know what each value means, which checks have already passed, and which effects must still happen. It needs to keep this information without wasting memory on empty space or creating a large object for every small fact.

This is a tour of one design I'm working on in a WebAssembly engine: a tape for the program itself, a separate schedule for its work, and a compact store for facts about values.

## Where IR fits

The front end reads and validates WebAssembly. The back end produces machine code. Between them sits an **intermediate representation**, or IR: a form of the program designed to make analysis and optimization easier.

![Conceptual WebAssembly compiler pipeline, showing the IR between validation and machine-code generation](/images/posts/the-tape-pipeline.svg)

An IR can be represented in different ways. Trees are natural for nested expressions. Graphs make relationships between computations explicit. Flat arrays or arenas can store nodes close together and refer to them by index.

These choices can overlap. A graph can be stored in an array, and a tree can use indexed nodes rather than pointers. The question is not which shape always wins. It's which properties make the compiler's actual work simpler and cheaper.

## The tape

The IR I'm exploring uses a **tape**: a flat sequence of small, fixed-size nodes. Think of it as an array of records, or frames on a film strip.

Each node has an ID. The ID identifies a stable place in the tape, so another node can refer to it without holding a pointer to a separate heap object. Data that doesn't fit inside a fixed-size node can live in side storage.

![The tape is a strip of fixed-size nodes](/images/posts/the-tape-tape.png)

A pass can walk these nodes in order. That access pattern is friendly to caches, but cache locality isn't unique to tapes. Carefully designed trees and graph arenas can also keep data close together.

For me, the more useful property is that **a node doesn't have to move when the compiler changes the program**.

When a computation becomes unnecessary, a pass can turn its node into a Nop, an entry that does nothing. It stays at the same ID, and other nodes keep their numbers.

![A node becomes a Nop without moving the other nodes](/images/posts/the-tape-nop.png)

Stable IDs also give the compiler a consistent way to refer to facts about a node. Those facts may need to be updated when the program changes, but unrelated node IDs don't shift just because an edit happened.

That still leaves a question: if the nodes stay in place, how can the compiler change the order of computations?

## Computation and execution order

**There are two structures, and they do different jobs.**

The *instruction tape* holds the nodes. Each node describes a computation or an effect, and its ID stays stable.

The *scheduler* holds an ordered list of node IDs for work that must be materialized or executed. To **materialize** a value is to produce it so later work can use it.

The scheduler changes the order of work without changing where the nodes live.

![A fixed instruction tape and a separate scheduler that reorders node IDs](/images/posts/the-tape-scheduler.svg)

Suppose node #9 is an addition that doesn't depend on the surrounding work. To schedule it earlier, the compiler moves the number **9** in the scheduler's list. The contents of node #9 stay in place. Nothing else has to be copied or renumbered.

Not every reorder is allowed. A read must respect its dependencies and required checks. Stores, calls, and other effects must keep the order that preserves the program's behavior. The scheduler provides freedom only where that freedom is safe.

Some nodes also represent small internal steps that don't need separate entries in the scheduler.

This is a key distinction from simply executing a linear bytecode stream in storage order. The program's representation and its execution order are no longer the same thing.

## Separate values from effects

An instruction can both compute a value and affect the program. A load produces data, but it can also trap on an invalid access. A store changes memory. A call may change state or trap even when its result is unused.

On this tape, the value-producing work and the effects are represented separately. A read has its own entry, while a nearby guard represents checks such as bounds or reference validity.

![A read and its required guard occupy separate entries](/images/posts/the-tape-split.png)

That separation lets an optimization pass ask two questions instead of one: **do we still need this value, and do we still need this effect?**

It doesn't make memory reads freely movable. Dependencies on memory state and required checks still matter. It does make those requirements explicit, so a pass can remove or reorder work without silently changing the program.

## What the compiler knows

Optimization passes need facts. A fact is a small statement about a value: a reference isn't null, a size is known, or an index lies within a range.

The number of *possible* facts can be much larger than the number the compiler actually knows. This is where memory use becomes a design problem of its own.

### Why the facts live in a B-tree

I could use a flat sparse array for facts. Indexing it would be straightforward. But when most possible fact slots are empty, paying for a large range of unused slots is precisely what I want to avoid.

**The goal is to use less memory.** The fact store should allocate space for facts that exist, rather than reserve space for facts that might exist.

I use a B-tree for that store. Its pages hold multiple sorted keys, so facts can be kept compactly as they are discovered. The tree also supports lookups, insertion, deletion, and scans of neighboring keys without requiring a huge mostly empty index.

![A B-tree organizes fact keys in sorted pages](/images/posts/the-tape-btree.png)

There are tradeoffs. A tree requires navigation and sometimes page splits; a direct array lookup can be simpler and faster. The B-tree isn't guaranteed to use the least memory for every workload. It's a useful balance for this one: **avoid unused slots while keeping fact operations practical**.

Facts are ordered by value and then by kind. The kinds used here describe what a value is, what it is not, its size, and its range. Facts about one value appear together in key order, making them easy to scan.

![Facts about one value are grouped by kind](/images/posts/the-tape-kinds.png)

The tape stores the program. The B-tree stores what the compiler knows about it. They solve different problems.

### Where facts are valid

A program can take different paths. The compiler represents those paths with a **control flow graph**: blocks of instructions connected by possible jumps.

![Control flow blocks joined by edges that carry facts](/images/posts/the-tape-cfg.png)

If one block checks a value, later work along that path may use the result. If two paths join, the compiler can trust only facts that hold on both incoming paths. A change to relevant state can also invalidate a fact.

The B-tree answers *what do we know?* The control flow graph helps answer *where can we rely on it?*

## Putting it all together

### Remove a check we already proved

Consider this small example in WebAssembly's text format, or WAT:

~~~wat
(if (result i32)
  (i32.lt_u (local.get $i) (array.len (local.get $a)))
  (then
    (array.get $arr (local.get $a) (local.get $i)))
  (else
    (i32.const 0)))
~~~

In plain words: if the index is smaller than the array's length, read that element. Otherwise, return zero.

On the true branch, the unsigned comparison establishes that the index is in bounds for the checked array. If the read uses the same array and index, and nothing has invalidated that fact, a second bounds check is unnecessary.

![A proven bounds fact removes the redundant bounds guard while keeping the read](/images/posts/the-tape-guard-elimination.svg)

The compiler can remove that specific guard while keeping the read and any other checks that still matter. The graph tells it where the proof applies. The fact store holds the proof. The separate effect entry gives the compiler something precise to remove.

### Remove dead work without removing traps

Dead code is work whose result nobody uses. Removing it sounds easy until the operation could still trap, write memory, or perform a call.

A pass can use value-use counts to find computations whose results aren't needed. It can replace a dead value node with a Nop, then reduce the use counts of that node's inputs. This can expose an entire chain of unnecessary computations.

But a required guard remains a separate scheduled effect. Removing an unused value does not mean removing a trap the original program would have taken.

![Unused computations disappear while a required guard remains](/images/posts/the-tape-dce.png)

The work disappears. The alarm remains.

## Why this design matters

The pieces reinforce each other. Small, fixed-size tape nodes avoid a separate heap object for each computation. Stable node IDs make local edits simple. A separate scheduler moves independent work without moving its nodes. Explicit effects make it possible to remove a value while keeping required behavior. A B-tree avoids allocating a large, mostly empty space for facts.

There are costs, too. A scheduler adds an extra layer of indirection. Nops leave unused tape slots until the representation is rebuilt or compacted. A B-tree trades direct array indexing for compact storage and ordered operations. Those costs need measurement, not assumptions.

The main goal isn't to prove that a tape beats every other IR. It's to keep the compiler's memory footprint and compilation work under control while still giving optimization passes the information they need.

A tape is a humble shape. But a few deliberate separations—nodes from their schedule, values from their effects, and the program from its facts—can make that humble shape useful.
