Consider this small program:

~~~js
const unused = 4 + 8;
console.log("Hello");
~~~

Nobody uses the result of the addition. A compiler can remove it and leave:

~~~js
console.log("Hello");
~~~

This is an **optimization**: the program does less work but still behaves the same way. The addition can go away. The message must still appear.

Now imagine doing this for a large program. The compiler must find unnecessary work without removing something that matters. And the compiler itself has limits: it must not take too long or use too much memory.

This article is about how I'm trying to make those decisions inexpensive. The main idea is a simple data structure called a **tape**, with a few important parts kept separate.

## Why a compiler needs its own view of a program

A compiler turns a program into instructions for a machine. A WebAssembly compiler does this for WebAssembly, a portable format that different computers can run.

Between reading WebAssembly and generating machine code, the compiler uses an **intermediate representation**, or **IR**. Think of it as the compiler's working copy of the program. It holds the information needed to improve the code before the machine runs it.

![A WebAssembly compiler reads and validates input, improves an intermediate representation, and generates machine code](/images/posts/the-tape-pipeline.svg)

There are many ways to store this working copy. A tree can represent nested calculations. A graph can connect work that depends on other work. An array can keep small records in order.

These choices can overlap: a graph can use an array for storage. No one shape is best for every compiler. The useful question is which shape keeps *this* compiler's work simple and cheap.

## The tape: small entries with permanent numbers

My working copy is a tape: a sequence of small, numbered entries. You can picture an array or a strip of film.

An entry, or **node**, describes one piece of work. For example:

~~~text
#7   Constant 4
#9   Constant 8
#12  Add #7 and #9
~~~

Node #12 tells the compiler to add the results of nodes #7 and #9. It refers to their numbers, not to separate objects scattered through memory.

![The tape is a sequence of small, fixed-size entries](/images/posts/the-tape-tape.png)

Each node takes just **16 bytes**. Information that does not fit can live in separate storage. A compiler pass—a step that examines or improves code—can walk the entries in order without following a long chain of object pointers.

The more important benefit is that the numbers stay stable.

If node #12 is no longer needed, the compiler can mark it as **NOP**, which means *no operation*. Node #12 keeps its place. Nodes that refer to other entries do not need new numbers.

![Turning a node into a NOP leaves other node numbers unchanged](/images/posts/the-tape-nop.png)

This keeps changes small. But how can we change the order of work if the nodes never move?

## Changing the order without moving nodes

The compiler keeps two different lists.

The **tape** stores what each node means. The **scheduler** stores the order in which the required work should run. Its entries are node numbers, not copies of the nodes.

![The tape stores fixed nodes while a separate schedule holds their execution order](/images/posts/the-tape-scheduler.svg)

Suppose an addition is independent of nearby work. To do it earlier, the compiler moves its number in the scheduler. The node itself stays put.

This saves the work of copying nodes or repairing references. It also lets different optimization steps change the order without rebuilding the tape.

Of course, not everything can move. A read must wait for its required checks and inputs. A store or call may change the program's state, so its order must still preserve the program's behavior.

The key distinction is simple: **where a computation is stored is not the same as when it runs**.

## Keeping the work that still matters

Some operations do more than calculate a value.

A read may fail because an address is invalid. A store changes memory. A function call might write data or produce a visible result. A **trap** is an error that stops WebAssembly execution, and an **effect** is an action whose behavior must be preserved.

In many representations, the calculation and its effects are treated as one instruction. My tape gives them separate entries. For example, an array read can have one entry for the value and another for its required guard, or check.

![A read and the check that protects it are separate entries](/images/posts/the-tape-split.png)

That changes the question an optimizer asks. It no longer has to decide whether the entire instruction stays or goes. It can ask:

**Is the value still needed? Is the check or effect still needed?**

If the value is unused, its calculation may disappear. If the check can still trap, the check stays. The scheduler keeps it in the required order.

This does not mean that all reads can move freely. Memory dependencies and required checks still apply. The separation simply makes those rules easier to enforce.

## Remembering what the compiler knows

To remove work safely, the compiler needs **facts**: small statements it has proved about the program.

For example, it may know that a reference is not null, an array has a certain length, or an index is within the array's bounds.

But it does not know every possible fact about every value. Imagine reserving a huge table with a slot for each fact the compiler *might* learn. Most slots could remain empty.

**I want to use memory for facts that exist, not for empty slots.**

So I store facts in a **B-tree**. It keeps groups of facts in sorted order and adds storage as new facts appear. The compiler can find a fact, add one, remove one, or look at nearby facts without reserving a huge mostly empty array.

![Known facts arranged in ordered B-tree pages](/images/posts/the-tape-btree.png)

A B-tree still has costs. Searching through pages takes work, and a direct array lookup may be faster. Here the main reason for the choice is to keep memory use low while making queries practical.

Facts also need a place where they are valid. A program can take different paths after a condition. The compiler keeps a **control flow graph**: a map of blocks connected by the paths the program can take.

![Different program paths meet at a join that can trust only facts common to both paths](/images/posts/the-tape-cfg.png)

If a check succeeds on one path, later work on that path may use the result. If two paths meet, the compiler keeps only facts that hold on both paths. It must also stop trusting facts when something relevant changes.

The B-tree stores *what the compiler knows*. The control flow graph helps decide *where that knowledge applies*.

## Removing more unnecessary work

Now the parts begin to work together.

### Remove a check we already passed

Consider a familiar example:

~~~js
if (index >= 0 && index < items.length) {
    use(items[index]);
}
~~~

The condition checks that the index is in bounds. Reading the element normally requires a bounds check too.

If the compiler proves that the same array and index are used, and nothing has invalidated the result, it can remove the repeated bounds check. It must still preserve other checks or effects that remain necessary.

![A proven condition lets the compiler remove a repeated bounds check but keep the read](/images/posts/the-tape-guard-elimination.svg)

The saved fact supplies the proof. The separate guard supplies a precise thing to remove.

### Remove unused calculations without losing traps

The same idea helps with **dead code elimination**, or **DCE**. Dead code is work that no longer has a useful result.

The compiler can count how many times a calculated value is used. If nobody needs it, the computation may become a NOP. Its inputs may then become unused too, so one removal can expose another.

Required effects and traps still stay.

![Dead computations are removed while their required guard remains](/images/posts/the-tape-dce.png)

The work disappears. The alarm remains.

### Make each cleanup help the next one

This is where the separate scheduler becomes especially useful.

The DCE families work together. Removing an unused computation can expose more unused values and even whole blocks that no longer need to execute. Dead nodes and blocks can then be removed from the **active schedule**, even while their original storage positions remain available on the tape.

Later optimization passes have fewer scheduled entries to examine. They can become faster, and their simplifications can expose still more dead code.

![Dead-code removal shrinks the active schedule and helps later optimization passes](/images/posts/the-tape-dce-cycle.svg)

This does not mean every extra pass is free or useful. The benefit fades when a round finds little more to remove. The goal is to repeat cleanup while it pays for itself.

## Removing arguments nobody uses

Here's another example:

~~~js
function show(unusedValue, message) {
    console.log(message);
}

show(calculateSomething(), "Hello");
~~~

The function never reads its first parameter. Why pass the result of \`calculateSomething()\`?

This is **dead argument elimination**, or **DAE**. It finds parameters that no execution needs and lets the compiler omit those values from calls. The version discussed here is still in development.

There are three parts to the idea.

### Find the unused parameter

The compiler checks whether the function reads the parameter. It also follows cases where a parameter is only passed to another function. A value is needed if some real use eventually demands it.

### Remove only the unused value

Even if the parameter is unused, \`calculateSomething()\` might change state or fail. Those effects must still happen.

The compiler can turn the dead argument's value calculation into a NOP while leaving its separate checks and effects in the scheduler. If another part of the program uses the same calculated value, that live use stays.

![The unused argument becomes a NOP while its guard and side effect still execute](/images/posts/the-tape-dae-effects.svg)

### Skip the argument when generating machine code

The compiler records which parameter positions are needed in a small set of yes/no flags, called a **mask**. The original call entry remains unchanged. When the compiler generates machine code, it consults the mask and passes only the needed arguments.

![The original argument positions stay on the tape while native code passes only the needed arguments](/images/posts/the-tape-dae-mask.svg)

Nothing needs to check the mask when the program runs. The decision has already been made during compilation.

DAE can also make the next DCE cleanup more useful. Once the call no longer needs an argument's value, its unused calculation and inputs may disappear.

## Why the design matters

Each part solves a small problem. The tape keeps node IDs stable. The scheduler lets work move without moving nodes. Separate checks and effects let the compiler remove calculations safely. The fact store avoids reserving large areas for information it does not have.

The parts become more useful together. One optimization removes work. DCE removes the dead values and blocks that remain. The active schedule gets shorter, so later passes can spend less time on code that no longer matters.

This approach still has tradeoffs. The scheduler needs its own storage. NOPs can leave unused slots in the tape. A B-tree is not always the fastest or smallest fact store. Those costs need measurements.

The goal is not to prove that a tape beats every other compiler design. It is to make useful optimizations without paying too much time or memory to apply them.

**The compiler can change less, while the program does less.**

## For the curious: implementation details

The main idea does not depend on knowing the exact data layout. These details show how it works.

### The 16-byte node

Here is a C-style view of the fixed-size record:

~~~c
#include <stdint.h>

typedef struct {
    uint8_t kind;        // What operation this node represents
    uint8_t reserved[3]; // Padding
    uint32_t a;
    uint32_t b;
    uint32_t c;
} TapeNode;

_Static_assert(sizeof(TapeNode) == 16, "TapeNode size");
~~~

The \`kind\` determines how the three 32-bit fields are used. Depending on the operation, a field may hold an input node ID, an immediate value, or an offset into side storage. This is an illustration of the internal layout, not a public C API.

![A 16-byte node has a kind byte, padding, and three 32-bit fields](/images/posts/the-tape-node-layout.svg)

The calculated values use **static single assignment (SSA)** identities: each value has one definition, and its users refer to that identity. Stable node IDs make those references inexpensive to maintain.

### Facts are grouped by value

The fact store orders keys first by value, then by the kind of fact. Related facts can be read together.

![Several facts about one value are stored next to each other in key order](/images/posts/the-tape-kinds.png)

A small, packed flag can represent a simple yes/no fact. The B-tree is more useful for sparse, richer information whose possible keys greatly outnumber the stored keys.

### An exact WebAssembly bounds example

This example uses WebAssembly text format, or **WAT**:

~~~wat
(if (result i32)
  (i32.lt_u (local.get $i) (array.len (local.get $a)))
  (then
    (array.get $arr (local.get $a) (local.get $i)))
  (else
    (i32.const 0)))
~~~

On the true branch, the unsigned comparison establishes \`i < array.len(a)\`. If the same array and index reach the read without any change that invalidates the proof, the repeated bounds check is redundant. A required null check, trap, or other effect must remain unless it has its own proof.

### How DCE and DAE stay inexpensive

DCE starts with use counts and an active schedule. Removing a dead result can reduce the uses of its inputs and uncover more dead work. The DCE families also remove dead blocks and compact the active schedule. They do not have to renumber the tape's node storage.

DAE marks parameters that are actually read. It also records **forwarding links**: cases where a parameter is passed into another parameter slot, including calls and control-flow edges. A **worklist** is simply a queue of positions still needing analysis. Demand moves backward along forwarding links. A cycle that only forwards a value does not count as a real use.

The marking cost is \`O(P + E)\`, where \`P\` is the number of parameter positions and \`E\` is the number of forwarding links. A **packed bitset** stores the decisions, using one bit for each position.

Not every function can have its private arguments removed. The compiler protects entries that external callers can reach, as well as imports, start functions, address-taken functions, and possible indirect-call targets. In this command-line setting, an export alone does not make an entry externally callable.

The shared WebAssembly function type stays unchanged. The private mask controls argument handling during code generation, including direct and tail calls, block-edge transfers, function-entry setup, and local storage planning. The **calling convention**—the rules for passing arguments—changes only for eligible private calls.

These rules avoid rebuilding the tape, rewriting each call's argument list, or adding a runtime check. And because effects remain separate scheduled nodes, deleting an unused argument value does not delete a required trap or side effect.
