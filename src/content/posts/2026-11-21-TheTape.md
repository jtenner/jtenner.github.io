All compilers have a middle. The front end reads the program you wrote. The back end outputs the program the machine wants. Between them is a private version of your program. You don't write it. You don't run it. It's private because it's the easiest version to improve.

In the engine I work on, it's a tape.

A tape is a tape. Just like you think. A bunch of instructions lined up. One after the other. All that same small size. Like frames in a film strip. You read the program by walking the strip. No tree to climb. No web of pointers to follow. Want to change the program? Walk the strip. Make changes. It's easy. Simple tools for simple shapes. A strip is about as simple as a shape can be.

![The tape: a strip of small entries, read by walking it](/images/posts/the-tape-tape.png)

The interesting choice isn't the strip. The interesting choice is what you put on the strip.

## Split every instruction into two

A regular instruction does two jobs at once: it computes a value, and it has effects on the world. A load computes the value it reads, and it can fail if the address is bad. A store changes memory. A call can do anything at all.

On the tape, those two jobs become two different entries: one entry for the value, and one entry for each effect, in order, next to the work it belongs to. For a load, the first entry is the read itself. Next to it sits a little guard entry that holds the checks: is the address in bounds, is this reference valid, is this the right type? The guard can stop the program, and the read cannot. They travel together, but they are not the same thing, and the tape never confuses them.

![One instruction split into two entries: the read and the guard](/images/posts/the-tape-split.png)

It seems like such a little bookkeeping trick, but it changes everything that comes after.

## What is so important about this shape?

First, neighbors. The entries that influence each other are close on the tape. The work a processor does is inside a core. Next to the core is a little fast memory called the L1 cache. The L1 is like a shelf near your desk. The main memory is a warehouse far away. The things on the shelf are easily accessible. The things in the warehouse require a trip. As a pass takes a walk down the tape, in order, the next entries the pass needs are often on the shelf because neighbors come together. The tree shape spreads the same entries throughout the warehouse. Each step may require a trip. And the core waits.

![The L1 cache as a shelf by the desk, and the tape as nodes in a row](/images/posts/the-tape-cache.png)

Second, the order is separate from the computation. The computation is in the tape. Each node specifies what a value is. It specifies what it uses. Another list, the scheduler, specifies the order. The scheduler specifies which nodes' values to make real. This is called materializing. It specifies the order to materialize the values. If you want to move an instruction, you move its number in the scheduler list. You don't move the node. You don't copy anything. You don't renumber anything. Also, a node may contain a little cluster of steps inside it. These steps are implied. The scheduler doesn't even know about them. The scheduler only specifies which values to materialize.

![The computation tape with numbered nodes, and the scheduler as a separate list of numbers](/images/posts/the-tape-scheduler.png)

Third, to delete a computation, that's just one little edit. You change the node to a Nop. A Nop is a node that does nothing. The node stays in the same place on the tape. It stays with the same number. All references to it still go to the right place. You don't move any other entry. You don't change any other entry.

![A node turned into a Nop, in place, with its number kept](/images/posts/the-tape-nop.png)

There are two more gifts that come with this shape for free. The number of a node never changes. So facts about a node, that were written down, remain correct as the tape is edited around the node. New nodes are added at the end of the tape. So adding stuff doesn't disturb what was already there. Each time you take a pass over the program, you take one walk over one strip. From start to finish.

## Where facts live

The passes that walk the tape work from facts, and the facts need a home.

A fact is one small true statement about one value. One compile makes millions of facts, so the compiler keeps them in a store, a place that keeps facts for later use.

The store has three jobs. It must answer the question "Is this fact here?" with a small cost, and it must keep the facts in order, because many questions are about neighbours. Order means the facts stand in a line, from the smallest value to the largest value. And it must take one new fact at a time, cheaply, while the build is still going.

A hash set is a store that many people know, but it has the wrong shape for this job. In a hash set, a formula chooses the place of each item, and the formula mixes the order on purpose. A hash set answers one question very well: is this exact item here? But it cannot answer the questions proof work asks each day: which facts stand between two values, which facts two stores share, and what the strongest fact about one value is.

The store is a B-tree, a store made of pages. A page is a box, and one page holds one short row of facts in order. The top page holds guide keys, and a guide key is a number that shows which page below can hold a fact.

![A card, a box of cards, and a guide box](/images/posts/the-tape-shapes.png)

To find a fact, the reader hops from page to page. A hop is one move from a page to a page below it, so the reader reads the guide keys, takes the correct branch, and hops again. Each hop reads one small page, so three or four hops find one fact in millions of facts, and the question "Is this fact here?" stays cheap.

![The guide box at the top, fact boxes below](/images/posts/the-tape-btree.png)

An insert puts a new fact into the store. The reader hops to the page for the new fact and puts the fact in its correct place in the row. When a page is full, the page splits into two pages and the middle fact moves up to the page above, which keeps each row in order and keeps all branches at the same depth. The rules that stay true through all of this are the invariant, and each insert fixes the invariant during the change.

![An insert: hop to the box, put the fact in, and a full box splits](/images/posts/the-tape-insert.png)

A page is also one short row in one place in memory, so one trip to the warehouse moves the whole page to the shelf. After that, questions about facts near each other read the shelf and do not go to the warehouse. Order in the tree gives closeness in memory, and closeness gives speed.

![One trip moves the whole box to the shelf](/images/posts/the-tape-page-locality.png)

Facts about one value stand in order by kind, and a kind is the type of a fact. The kinds are four: what a value is, what a value is not, a size, and a range. All the facts about one value make one run, all of them in one place, so the whole tree is a line of runs. To ask what the compiler knows about a value, the reader reads one run.

![Facts about one value, ordered by kind, as one run](/images/posts/the-tape-kinds.png)

The store holds the facts still. The graph is where they move.

## Facts ride the graph

Programs have branches. A block of instructions ends with a jump. And the next block of instructions depends on how the program got there. Lay out the blocks. Join them up with their jumps. You have a graph. The control flow graph. All the optimizers you've ever heard of work with some version of this graph.

![Blocks joined by jumps, with facts riding the edges](/images/posts/the-tape-cfg.png)

Facts ride the graph. Along the edges. So if you checked a value in one block. The blocks after it can know that. If two paths meet. The joined block can only trust what they both agree on. Where you have a strong enough fact. Work disappears. If you check a value twice. It's a check you already passed. So the second check goes away. Nobody guessed. The proof rides the graph from the place of the first check to the place of the second one.

This is where the split pays off a second time. Proof is about values, and on the tape the values stand on their own entries, apart from the effects. The facts can ride the graph without dragging the effects along.

Here is one small case, in WebAssembly text form. Programmers call that form WAT.

```wat
(if (i32.lt_u (local.get $i) (array.len (local.get $a)))
  (then
    (array.get $arr (local.get $a) (local.get $i))))
```

Read it in plain words. If the index is smaller than the length of the array, read the element at that index.

On the tape, the read carries its guard beside it, the same split from the start of this post.

## Remove dead code without breaking the alarms

Dead code is work that's not being used. You compute a value. But nothing ever reads it. All real programs have dead weight. Like a workshop. With offcuts.

It's easy to remove. And usually scary. The fear is earned: instructions have effects. If you remove the wrong one. You might remove a check. Or a write. Or an important call. So compilers get scared. They leave work in there. Work they can't prove it's safe to remove.

The split makes the fear go away. Walk the tape backwards. Count the uses. If nobody uses the result of an entry. It's a candidate. If the entry is just a computation. It dies. And the uses of its inputs go down. So you can kill chains of dead work in one walk. If it's a read, it can die, since the read itself does nothing to the world. The kill is the small edit from earlier in this post: the entry turns into a Nop and keeps its number. But the guard stays. It's a separate entry. Its own place in the order. And it still stops the program. Right where the original code would have stopped. You removed the work. You left the alarm.

![The backward walk: dead work crossed out, the guard kept](/images/posts/the-tape-dce.png)

That's the whole trick. But it's not really a trick. Separate the computation of a step. From what it does to the world. Then improvement is not a negotiation with the fear. You have what is known, kept in the store and riding the graph. You have what is dead, from the use counts. Effects stay in their order. Untouched. While the values around them get proven. And moved. And cleaned away.

A tape is a humble shape. But humble shapes go a long way. If you make the right split.
